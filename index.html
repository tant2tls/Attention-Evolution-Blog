The attention journey

The past is expensive.
How attention learned to carry less.

Start with Llama’s growing key–value cache. Then follow the windows, compressed histories, recurrent states and shared buffers that change what a model keeps—and how much work it does to look back.

01

Introduction

Longer contexts make attention expensive in two ways: there is more history to read and more state to keep. New attention designs try to reduce one or both costs.

Imagine asking a coding agent to fix a bug. It opens files, reads logs and tries a patch. An hour later, its context may contain all those steps. To choose what to write next, it needs a way to connect the current task with useful details from that history. Attention makes those connections. A token is one piece of the text the model processes, often part of a word.

1. The cost of reading history

Reading a prompt means building connections across its tokens. With full attention, doubling a long prompt roughly quadruples the number of token pairs to consider: this is O(T²) work for prompt length T. Generating one more token is different. That token looks back through the existing history, so the core attention work for that step grows roughly in proportion to T. These two phases are called prefill and decode.

2. The cost of storing history

The model also keeps information from earlier tokens so it can reuse it. This is the key–value, or KV, cache. With ordinary full-history attention, twice as much context means roughly twice as much cached history. More layers and more simultaneous requests add to the bill. A long agent session therefore uses memory that could otherwise serve another request.

These pressures help explain why attention has become more diverse. Local windows and sparse selection reduce which past entries are read. Compression reduces their representation size. Recurrent layers update a bounded state, while cross-layer sharing avoids keeping another copy. Each choice changes the balance between computation, storage and access to the past.

We explore six models: Llama 3.1 70B, MiMo V2.6, DeepSeek V4 Flash 0731, Qwen3.8 Flash-Next FP8, GLM-5.3 Flash and DeepSeek V4.1 Flash. This blog looks at their attention architectures and the performance implications: how much state they store, how quickly they generate a token, and how they process a long prompt.

In our H100 measurements, Qwen3.8 has the fastest decode attention, while DeepSeek V4.1 has the smallest settled attention-state storage. Prefill tells a different story: MiMo is fastest at 16K context, and Qwen at 64K and 128K. We follow the architectural choices behind these results.

The starting point: scaled dot-product attention

Think of a token looking for useful information in the text it can see. The same operation repeats in several parallel attention heads.

Suppose a log says “the upload failed because the token expired.” Connecting “expired” with “token” helps interpret what happened. The model learns such connections through three vectors made from each token’s current representation:

Query · Q

Describes the information the current token is looking for.

Key · K

Describes an earlier token so a query can score how well it matches.

Value · V

Carries the information that contributes to the result when that token gets attention.

The formula puts this into four steps: score the keys, scale the scores, turn them into weights, then blend the values.

A=softmax(QKTdk+M)V

Q, K and V are the queries, keys and values projected from token representations. dk is the query/key dimension; the square-root factor controls score scale. The causal mask M adds 0 at allowed positions and −∞ at future positions. Softmax normalizes each query’s scores into weights.

The mask hides future tokens. Softmax makes the allowed weights add up to one, so the result is a weighted blend of values. During generation, saved K and V avoid rebuilding earlier tokens’ entries. That reuse saves computation, but the saved entries take memory. The designs below change what is kept and how it is read.

03

Attention variants

To understand the trade-offs, follow what each design reads, stores and reuses.

Keep two questions in mind: how much history stays in memory, and how much of it does a new query read? A model can keep a large archive but read only a few entries. Finding those entries also takes work. This is why “sparse attention” does not automatically mean a small cache or a faster step.

1. Share the heads: Llama’s starting point.

Start with several attention heads looking at the same text through different learned projections. Giving every query head its own keys and values repeats storage. Llama uses grouped-query attention (GQA): its 64 query heads share eight KV heads in each of 80 layers. This saves head storage while keeping all earlier tokens available. It still stores more entries as the conversation grows.

The causal triangle in the architecture explorer means a query can read earlier positions. It does not mean those positions receive equal attention weight.

2. Keep most work local: MiMo.

Many useful connections are nearby: a variable’s use and its recent definition, for example. MiMo limits 39 of its 48 layers to a moving, 128-token window. Once a token leaves that window, those layers can discard its cache entry. The other nine layers keep full-history access, providing a route to older information. Local caches level off; global caches keep growing.

3. Make history smaller: DeepSeek V4.

What if older history stayed available in fewer entries? DeepSeek V4 0731 keeps a recent window and compresses history into a smaller representation. Twenty-one layers use a fourfold-compressed path with an indexer; twenty use 128-fold compression. Two layers are window-only. An indexer is the selection mechanism: it scores candidate entries and chooses which ones the attention operation will read on the fourfold path. Compressing and selecting history saves storage and reading work, but it adds its own operations and buffers.

4. Update a state, then retrieve: Qwen and GLM.

Another option is to keep updating a working memory instead of appending a separate entry for every token. A recurrent layer does this with a fixed-size matrix. Its contents change with each token, but its shape does not grow with the conversation. Qwen uses Gated DeltaNet in 36 layers; GLM uses Kimi Delta Attention in 34. Both interleave these layers with sparse attention that can retrieve from a growing history. A fixed recurrent matrix therefore does not make the whole model’s attention storage constant.

The stored representations also differ. Qwen retains K/V for its sparse layers; GLM uses compressed KV latents. Both need selection metadata, and their recurrent state includes higher-precision buffers. “FP8 KV” describes only part of that storage.

5. Stop storing it again: DeepSeek V4.1.

So far, we have changed what each layer keeps. V4.1 also changes who keeps it. Its configuration identifies four layers that own the long-range KV buffers. Later layers can read those buffers while keeping their own recent windows, much as several readers can consult one shared archive. We count the archive once at its owner; reading it does not create another stored copy.

Sharing also changes prefill. In the measured 8,192-token chunk at 64K, 20 V4.1 layers processed all 8,192 positions; the other 20 processed 128 positions each. The number of model layers alone does not describe the amount of prompt work executed.

Try MiMo first. Its 39 local layers might suggest that local state should dominate the bar. At long context, the opposite happens: the nine global layers keep accumulating KV while the local windows stay bounded. Layer count and memory share answer different questions. Qwen and GLM have bounded recurrent matrices alongside growing sparse-layer state. DeepSeek’s compression and V4.1’s sharing reduce different kinds of repetition.

FP8 is not one universal layout. We tried FP8 KV for all six models. MiMo could not execute that path with this build’s Diff-KV/sink backend, so it uses BF16. DeepSeek uses a packed FP8 format; index, tail and recurrent buffers can use other dtypes. Qwen’s two KV heads are replicated four ways under TP8. These implementation choices are part of the measured storage.

05

Decode

Qwen has the shortest measured decode-attention time at every supported context and batch shown here.

Decode is the repeated step of generating the next token from the history already built. With a batch of eight, the engine advances eight sequences in a step. At 64K and batch eight, the attention-module sum is 2.28 ms for Qwen, compared with 8.68 ms for Llama. V4.1, despite holding the least state, takes 3.93 ms. The ordering is a reminder that bytes alone do not determine execution time: selection, compression, projection and recurrent updates all cost work.

The context axis is logarithmic. Each repetition builds fresh state, completes 50 untimed decode steps, then measures 50 pure decode steps with the actual batch checked. Context grows during the interval. Llama stops at 64K; its 128K point is unsupported.

A probe has a cost, too.

CUDA events let us measure the attention regions, including when graphs replay. They also slow execution. We ran matched controls without the probes. At 64K and batch eight, attributing the entire whole-model slowdown to the attention regions gives a conservative sensitivity range. This is an accounting assumption—not a confidence interval or an exact overhead correction.

64K, batch eight: measured attention and probe sensitivity

The dark line spans measured attention minus the positive control slowdown, up to measured attention.

The attention fraction is also deployment-specific. At this point Qwen’s instrumented attention accounts for about 29% of its instrumented model-forward-plus-logits time; Llama’s accounts for about 54%. These fractions do not measure serving throughput, request latency or response quality. Nor do they isolate an attention core from its projections and state preparation.

How time is aggregated. Events bracket attention modules. We sum layer intervals on each rank and take the maximum rank value; the model window is measured separately. The result is a component-time metric, not a distributed critical-path measurement. Prefill intervals can include GPU idle gaps between host launches. No kernel-sum, hardware-bandwidth or architecture-only claim is made.
06

Prefill

MiMo has the lowest measured prefill-attention time at 16K. Qwen is lowest at 64K and 128K.

Before an agent can answer, the model must process the input it has been given. That is prefill: many new tokens arrive together, rather than one new token per sequence. For example, an 8K chunk ending at 64K adds 8K new tokens to 56K tokens already processed. We compare this same chunk size ending at 16K, 64K and 128K, with earlier state already populated. These times describe one chunk, not the entire prompt or time to first token.

At 64K, the attention-module sum is 358.1 ms for Llama, 63.9 ms for Qwen and 69.5 ms for MiMo. V4.1 takes 72.1 ms. GLM’s lower decode-attention time than Llama does not carry over to a similarly large prefill reduction. The phase matters.

The checkpoint alone does not tell us which positions execute. In V4.1’s 64K trial, only half the layers processed the entire new chunk; the rest processed a 128-position tail. A claim such as “40 layers times 8K tokens” would miss that asymmetry. The saved per-layer position counts make it visible.

The separate 1K first-chunk measurement

The first 1,024-token chunk has no preceding history and is smaller than the 8K chunks above. Its event intervals are particularly sensitive to host-launch gaps. Treat it as a separate workload.

What the journey tells us.

Llama makes the cost of keeping everything visible. MiMo bounds most layers’ history. DeepSeek compresses it, Qwen and GLM combine recurrent updates with retrieval, and V4.1 shares storage across layers. Each reduces a different source of work or duplication. The measurements show where those choices help on this H100 deployment; they also show why no single “smaller cache means faster attention” rule survives both phases.
