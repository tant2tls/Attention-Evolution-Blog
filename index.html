How frontier attention evolved.

Llama 3.1 stores keys and values for every previous token in every layer. Newer systems rethink what to store, what to retrieve, and what to recompute. The design choice matters as much as the model's parameter count.

01

Introduction

Attention is no longer one algorithm repeated across every layer. The last few generations changed which tokens can be seen, how their information is represented, and where that state is stored.

This article follows a useful narrative: the bottleneck → the architectural response → the new trade-off. We start from the Llama 3.1 70B grouped-query attention (GQA) baseline, then explore DeepSeek V4 Flash, DeepSeek V4.1 Flash, MiMo-V2.6-Flash-MOPD, Qwen3.8-Flash-Next and GLM-5.3-Flash. We focus on attention state, not benchmark quality or the full cost of MoE experts.

2017–19MHA → MQA

Global lookup works, but per-token cache grows; sharing KV heads reduces it.

2020–22Local + efficient kernels

Window and sparse patterns change what is read. FlashAttention changes how exact attention is executed.

2023–24GQA + MLA

Reduce KV replication or compress token history into latents.

2025Sparse + recurrence

Select a small history or update a bounded state instead.

2026Shared-state hybrids

Mix retrieval, recurrence, local windows and shared caches across layers.

Question 1

What is read?

All earlier tokens, a bounded window, selected positions, or a running state?

Question 2

What is stored?

Per-layer KV, compressed latent vectors, pooled index keys or shared state?

Question 3

What actually runs?

Different active parameters and prefill/decode paths, not just total weights.

Inspired in part by The Evolution of Attention (2017–2026). Its historical perspective is adapted here into model-specific systems analysis. FlashAttention is an implementation technique; GQA, sparse attention and recurrence are architectural choices—do not put them on one mutually exclusive axis.

Six architectures

Parameter counts, attention layouts and cache layouts are different dimensions. A 552B MoE does not activate 552B parameters per token; a 40-layer model does not necessarily allocate 40 independent global KV caches.

The parameter bars below distinguish core/backbone weights from conditional tables and auxiliary heads. Active parameter counts are vendor-reported approximations per token; they are not GPU memory usage. A model may need to keep many inactive expert weights resident to run at low latency.

03

Attention variants: what changes?

Different models solve different pieces of the same scaling problem. These six diagrams distinguish access patterns, state representations and inter-layer sharing.

The matrix diagrams use a small example sequence. A dark square means that a query can attend to that past position. The shared-state diagrams describe data flow instead of a literal attention matrix.

FlashAttention is not a seventh attention pattern. It speeds up the computation of supported attention operations through GPU-aware tiling and IO reduction. Sparse retrieval, recurrent state updates and shared KV compression can coexist with specialized high-performance kernels.
04

Attention storage memory

The useful comparison is memory owned by one layer and memory stored across the whole model. Multiply by the number of layers only when those layers really own separate caches.

A 70B GQA baseline needs KV for all 80 layers. MiMo needs full-history KV for just nine layers and a bounded window in 39 others. Qwen and GLM mix context-growing KV with fixed recurrent states. V4.1 introduces a shared global store whose bytes should not be multiplied by its 40 layers.

05

Decode attention performance

At decode, the new query is short. The crucial variables are the cached state it reads, memory traffic, indexer work and recurrent updates—not simply model parameter count.

To interpret GPU traces, separate the cost of selecting history (indexers), reading stored KV, updating recurrent state and projecting Q/K/V. The figure below is intentionally synthetic to demonstrate the planned plot before running Llama 3.1 under the same 8×H100 setup.

Illustrative attention-kernel latency per decode step

Simulated ms/step for selected context; includes only attention-related components and recurrent updates.

Synthetic timing, not measured
A low attention-kernel time does not prove high end-to-end tokens/sec. Expert GEMMs, tensor-parallel communication, scheduler behavior and kernel maturity can dominate total decode time.

Measure separately

  • Attention kernel time and HBM bytes per decode step.
  • Indexer/top-k cost, compressed-KV dequantization, recurrent update.
  • B=1, B=8 and B=16 at 1K / 16K / 64K / 128K.

Interpret carefully

  • Record layer count and actual state dtype for each checkpoint.
  • Report both summed GPU kernel time and wall-clock step latency; do not equate them.
  • Measure attention separately from end-to-end serving throughput.
06

Prefill attention performance

Prefill changes the compute question. A new chunk must connect its queries to the stored past. Dense GQA, local windows, sparse retrieval and recurrent state scans do very different amounts of work.

Experiments needed before publication

Controlled runs

  • Run Llama 3.1 70B with identical TP, KV dtype, prompt length and GPU settings.
  • Report peak reserved vs live allocated KV and fixed recurrent state, per layer and in total.
  • Profile prefill chunks and decode steps separately across context and batch sweeps.
  • Log kernels by attention core, indexer, state update, projection and communication.

Architectural caveats

  • For V4/V4.1, trace cache producers, cross-layer aliases and replay buffers instead of inferring from layer count.
  • For GLM/Qwen, include indexer and recurrent states—not just KV tensors.
  • State exactly which attention state format (FP4, FP8, BF16) is stored.
  • Do not attribute whole-model speed differences to attention alone.
Prototype evidence policy: model cards/configurations are referenced facts. Llama and MiMo cache math is derived from documented dimensions under explicit BF16 assumptions. Other memory component sizes and every performance number are illustrations until matched to the actual serving implementation and GPU traces.
